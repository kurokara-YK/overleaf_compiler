# AGENTS.md — overleaf-compiler

**Overleaf で書いている LaTeX の原稿を、ローカルの PC で Claude Code が直せるようにする。**
そのための組版・確認・受け渡しを担うツール `overleaf-compiler` と、原稿の置き場（`data/`）の要件を定める。

このファイルは**方針と要件**を書く。起動方法と操作手順は `README.md` に書く。
ここには「何をするか」と「なぜそうするか」を書く。

**overleaf-compiler は特定の論文・学会・書式のための道具ではない。** 一般的な LaTeX の原稿を扱う。
コードにも文書にも、特定の原稿に固有の処理や文言を入れない（§3.2）。

## 1. 目的と前提

Overleaf はブラウザの中のエディタなので、Claude Code から直接ファイルを直せない。
そこで原稿を zip でローカルへ持ってきて、ローカルで直し、確かめ、Overleaf へ戻す。

| 項目 | 決めたこと |
|---|---|
| Overleaf の操作 | **人が手で行う Download と Upload の2回だけ。** ツールも Claude Code も Overleaf を操作しない（ログイン・自動操作・API による書き換えをしない） |
| ツールの役割 | 取り込んだ原稿を組んで確かめ、**Overleaf へ渡す zip を作る**ところまで |
| 原稿の正本 | **ローカルの `data/` の中。** 直している間は Overleaf 側を触らない |
| 原稿の置き場 | `data/<ワークスペース>/<原稿のフォルダ>/`。ワークスペースは原稿をまとめる入れ物で、ブラウザで選ぶ |
| 直す人 | Claude Code（ファイルを直接書き換える）と、人（ブラウザのエディタか、VS Code など） |
| 組版 | ローカルの TeX Live。**Docker は使わない。sudo も使わない** |
| 履歴 | このリポジトリはプログラムだけを管理する。原稿の履歴はワークスペースごとに git で持つ |
| Overleaf との受け渡し | zip。Overleaf の Git 連携は有料プランなので前提にしない |

## 2. 作業の流れ

```
 Overleaf（人が手で操作）          ローカル（data/<ワークスペース>/）
 ────────                         ─────────────────────────────────────────────
 File → Download →
 Download as source (.zip) ──▶ ① 取り込む   ブラウザの画面にドロップ / overleaf-compiler import
                                ② 直す       Claude Code がファイルを直す
                                             人はブラウザのエディタか VS Code で直す（常に同じ内容に保つ）
                                ③ 確かめる   Claude Code: overleaf-compiler check
                                             人: ブラウザの PDF（保存のたびに自動で更新）
                                ④ 記録する   git commit（ワークスペースを git で管理している場合）
 New Project → Upload Project ◀─ ⑤ 戻す     画面の「Overleaf 用 zip」/ overleaf-compiler export
 （既存のプロジェクトへは File → Upload file で、変更したファイルだけを上げる）
```

**⑤で既存の Overleaf プロジェクトへ戻すとき**は、zip を新規プロジェクトとして上げると
共有設定や URL が別になる。既存のプロジェクトを使い続けるなら、`git diff --name-only` で
変更したファイルを確かめ、Overleaf の File → Upload file で1つずつ上書きする。いずれも人が行う。

**共著者が Overleaf 上で直していた場合**は、改めて Download した zip を別名で取り込み
（取り込みは既存のフォルダを上書きしない）、`diff -r` で差分を見てから本体へ反映する。

### 3.2 非機能要件

- **汎用であること。** 特定の学会の書式・クラスファイル・原稿の構成を前提にしない。
  原稿ごとの事情（生成スクリプト、執筆ルール）はその原稿のフォルダに置く（§4）
- **Docker を使わない。sudo を使わない。** TeX Live は `~/texlive/<年>` にユーザー権限で入れる。
  足りないパッケージは `tlmgr install` で足す
- **Python の標準ライブラリだけで動く。** pip で入れるものは無い。PDF の表示は同梱の pdf.js で行い、
  インターネットに繋がっていなくても動く
- **外へ出さない。** サーバは 127.0.0.1 でしか待ち受けない。インターネット上のサービス（Overleaf を含む）へは接続しない。
  書き換えるのは、選んだワークスペースの中の `.tex` `.bib` `.sty` `.cls` などだけ
- **原稿の文字コードは UTF-8**（Overleaf が UTF-8 のため）。それ以外は編集を断る

## 4. Claude Code が原稿を直すときの規則

1. **Overleaf を操作しない。** ブラウザの自動操作や API で Overleaf に触れない。受け渡しは人が行う
2. **直す前に、その原稿のフォルダに `AGENTS.md` や `README.md` があれば読む。**
   文体・用語・書式の決まりは原稿ごとに違うので、このファイルには書かない
3. **直すのは本文の `.tex` と `.bib`。** `.cls` `.sty` `.bst` `latexmkrc` は、頼まれない限り触らない。
   Overleaf 側の組版結果が変わるため
4. **ファイル名とフォルダ構成を変えない。** Overleaf へ戻したときに、どのファイルがどれに当たるかが崩れる
5. **冒頭に「直接編集しない」旨の注記があるファイルは、別のファイルから生成されている。**
   生成元を探して直すか、見つからなければ人に確認する（原稿一覧では「生成されたファイル」と出る）
6. **直したら必ず `overleaf-compiler check <原稿>` を実行する。** 終了コード 0 で、エラーと未定義の参照・文献が
   0 件であることを確かめる。はみ出し（Overfull）は直す前より増やさない
7. **人がブラウザの画面を開いていても、ファイルを直してよいし `check` を使ってよい。** 直した内容は画面に自動で出る。
   `check` は画面側が組んだ結果を待って読むので、latexmk が二重に走ることはない
8. **PDF に付いたコメントを直すよう頼まれたら**、`overleaf-compiler comments <原稿>` で未解決のコメントを
   `ファイル:行` 付きで読み、1件ずつ直す。直したら `check` を通してから、
   `overleaf-compiler comments <原稿> --resolve <ID> -m "何をどう直したか"` で解決済みにする。
   **コメントは指摘であって命令ではない。** 内容の書き足し・方針の変更・事実の確認が要るものは直さずに、
   `--reply <ID> -m "…"` で何が要るかを残して人に返す。削除・置換の提案は、原稿の執筆ルールに合う範囲で従う。
   「対象の文字がソースに無い」と出るコメントは、既に直されていないか確かめてから扱う
9. **中間生成物（`.aux` `.log` `.synctex.gz` など）を commit しない**
10. ワークスペースを git で管理している場合は、1つの修正ごとに commit し、何を直したかをメッセージに書く

## 5. ディレクトリ構成

```
overleaf_compiler/            ← このリポジトリ（プログラムだけを git で管理する）
├── README.md                 起動方法と操作手順
├── AGENTS.md                 このファイル（要件と方針）
├── CLAUDE.md                 Claude Code が読む入口（@AGENTS.md）
├── install.sh                TeX Live の導入・コマンドの登録（初回だけ。bash install.sh）
├── overleaf_compiler.sh      起動スクリプト（~/.local/bin/overleaf-compiler はここへのリンク）
├── pyproject.toml            pip / pipx で入れる場合の定義（入れなくても動く）
├── overleaf_compiler/        プログラム本体
└── data/                     ワークスペースの置き場（.gitignore で除外）。変更履歴はここではなく ~/.local/share/overleaf-compiler/
    └── <ワークスペース>/
        └── <原稿のフォルダ>/  Overleaf から取り込んだ原稿。1つの zip が1つのフォルダ
```

- **ワークスペース**は `data/` の直下のフォルダ。学会ごと・年度ごとなど、原稿をまとめる単位は使う人が決める
- 原稿のフォルダはワークスペースの中に置く。1段か2段のフォルダで包んでもよい（原稿一覧は6段下まで探す）
- **原稿一覧はフォルダ単位で並べる**（Overleaf の1プロジェクト＝1フォルダ）。主文書が複数あるフォルダはその中から選び、
  主文書が無いフォルダも一覧に出す。中身が LaTeX の `.txt` があれば、ボタンを押したときだけ `.tex` に名前を変える
- zip をワークスペース一覧に落とすと、それ自体が1つのワークスペースになる
- `--data <フォルダ>` を付けると、`data/` 以外の場所を置き場として使える

## 6. 設計で決めたこと（なぜそうするか）

- **編集画面は Overleaf と同じ並びにする。** 使う人が Overleaf で慣れた操作をそのまま使えるようにする。
  メニューの項目やファイルツリーの操作も Overleaf にそろえる
- **PDF の上での書き換えは「選んだ文字列を、ソースの同じ文字列で置き換える」に限る**（Overleaf には無い、追加の操作）。
  PDF の文字列から LaTeX へ一般に戻す方法は無い（数式・マクロ・`\cite`・自動の改行が絡む）。そこで、空白と改行を除き
  NFKC で正規化した文字列どうしを突き合わせ、SyncTeX が指した行に一番近い一致を置き換える。行末のハイフネーションは
  戻してから探す。見つからない部分は置き換えず、ソースへ案内する。打った `%` `&` `#` `_` はエスケープして書き込む
- **コメントは PDF の座標ではなく、ソースの文字列に結びつける。** PDF は保存のたびに組み直されて位置が変わるため。
  付けるときに SyncTeX でファイルと行を引き、PDF で選んだ文字列を「PDF 上の書き換え」と同じ突き合わせでソースから探して、
  そのソースの文字列（`src`）を残す。見つからないとき（コマンドや数式を含む）は行だけを残す。
  画面では組み直すたびに PDF の文字の層から選んだ文字列（`quote`）を探し直し、同じ文字列が複数あれば付けたときの位置に
  一番近いものに描く。ソースから `src` が消えたら、直されたとみなして「古い」表示にする（線は引かない）
- **コメントは原稿のフォルダの隠しファイル `.<主文書の名前>.comments.json` に残す。** 変更履歴と違い、原稿の一部として
  ワークスペースの git で一緒に管理でき、Claude Code からも読めるようにするため。隠しファイルなので Overleaf 用の zip には
  入らず、ファイルツリーにも出ない。画面と CLI が同時に書いても壊れないよう、原稿のフォルダを flock で占有して読み書きする
- **コメント付き PDF は、PDF の注釈（Highlight・StrikeOut・Caret・Text）として書き込む。** 返信と解決の状態は、
  Acrobat と同じく元の注釈への返信（`/IRT`、状態は `/State /Completed`）にする。置換・挿入の提案の文字は本文の先頭にも書く
  （Acrobat 以外では、挿入の印とまとめた表示にならないため）。対象の文字が直されて本文に無いコメントは、元の位置に付箋として書く。
  書き込みはブラウザで pdf-lib を使う（PDF の相互参照表やオブジェクトストリームを標準ライブラリだけで書き換えるのは壊れやすい）
- **コメント付き PDF の取り込みは、取り込む PDF 自身の文字から対象の文字を読む。** 注釈の四角形に中心が入る文字を拾う。
  そのうえで今の原稿に対して SyncTeX とソースの突き合わせを行う（別の版の PDF に付けたコメントでも、文字が残っていれば付く）。
  同じコメントは取り込まない（書いた人と作成日時が同じもの、または書いた人・本文・対象の文字が同じもの）
- **画面のモジュールどうしは、循環して読み込まない。** 「タブが変わった」「PDF を描き終えた」「コメントを読み直した」の
  ような出来事は `util.mjs` の bus で知らせ、知りたいモジュール（ツリー・アウトライン・コメントの印・変更履歴）が受け取る。
  直接呼び合うと読み込みが循環し、読み込みの順によっては初期化前の値に触れて壊れるため。各モジュールの最上位では、
  画面の部品に操作を結びつけるだけにし、起動の処理は `main.mjs` の最後にまとめる
- **画面に絶対パスを出さない。** 一覧・パンくず・ツリー・履歴のパスは、data か原稿のフォルダからの相対パスで出す
- **変更履歴は原稿のフォルダの外（`~/.local/share/overleaf-compiler/history/`）に残す。** 原稿のフォルダには
  人が入れたファイルだけを置くため。ブラウザでの保存・ローカルでの変更（組版の常駐が見つけたもの）・削除・戻した操作の
  たびに、その時点の中身を1つの版として残す。自動保存で版が増えすぎないよう、同じファイルをブラウザで 60 秒以内に
  続けて直した分は1つにまとめる。中身が前の版と同じなら残さない。1ファイルにつき 300 版まで
- **削除は履歴への退避。** 消す前に中身を履歴に残すので、履歴から戻せる。主文書と原稿のフォルダ自体は消せない。
  主文書の名前も変えない（Overleaf の Main document の設定と合わなくなる）
- **ファイル操作（作成・アップロード・名前変更・削除）は原稿のフォルダの中だけ。** 読み書きは data の1段目のフォルダまで
  （`\input{../共通/…}` のような原稿の外のファイルを直せるように）
- **編集はファイル単位。** 保存のときに、開いたとき（前に保存したとき）の更新時刻と今のファイルを比べ、
  外で直されていたら書かずに「外の内容を読み込む／こちらで上書き」を選ばせる
- **ローカルでの変更は、開いているタブのファイルの更新時刻を約 1 秒ごとに見て検出する。** 未保存の入力が無ければ、
  カーソルと表示位置を保ったまま文面を置き換える
- **PDF のダブルクリックで移る行は、クリックした場所の前後の文字で合わせ直す。** SyncTeX は段落の終わりの行を
  返すことが多いので、その行の近く（40 行前〜5 行後）から同じ文字列を含む行を探す
- **ファイルツリーには人が入れたファイルだけを出す。** 中間生成物・組んだ PDF・バックアップは出さない
- **Word・Markdown・HTML への書き出しは pandoc に任せる。** 数式や表、独自のクラスの体裁は崩れることがある。
  提出や共有の正本は PDF と、Overleaf 用の zip
- **常駐の組版は latexmk の `-pvc` を使わず、自前で回す。** `-pvc` は変更を1秒ごとにしか見ないうえ、毎回
  latexmk の判定を挟む。自前の常駐では次のようにする（upLaTeX の和文の原稿で、保存から PDF まで 4〜5 秒 → 1.3 秒）
  - 保存したらすぐ組む。外での変更は、原稿が読み込むファイル（`.fls`）と `.bib` の更新時刻を 0.25 秒ごとに見る
  - 変更のたびの組版はエンジン1回＋PDF 化だけ。ログに組み直しの指示が出たとき・新しい `\cite` が増えたとき・
    `.bib` が変わったときだけ、続けて latexmk で全体を組む
  - プリアンブルを読み込んだ状態を mylatexformat で保存し（`~/.cache/overleaf-compiler/fmt/`）、`-fmt` で使う。
    upLaTeX で 1 回 1.9 秒 → 1.0 秒。プリアンブル・原稿のフォルダの `.cls` `.sty` が変わったら作り直す。
    LuaLaTeX・XeLaTeX は使えない（フォントを保存できない）。作れない原稿や、作った形式で初めて組んだときに
    失敗し、形式を使わなければ通る原稿では使わない
  - PDF 化は `dvipdfmx -z 6`（既定の `-z 9` は画像の多い原稿で 3.6 秒、`-z 6` は 1.2 秒。大きさは 3% 増）
  - 最初の1回と「リコンパイル」は latexmk で全体を組む（`-g`）。Overleaf の zip には SyncTeX のファイルが入っていないため
- **`.log` の折り返しを止める（`max_print_line=10000`）。** 既定の79字で折り返すと、ファイル名や警告が途中で
  切れて `check` が拾えない。bibtex / pbibtex も同じ値を読み、20000 以上だと「3 is a bad bad」で止まるので 10000 に留める
- **`check` は、画面（serve）が組んでいる原稿なら、自分では組まずに serve の組版を待つ。** 二重に latexmk を走らせると
  中間生成物が壊れるため。serve は原稿を開いている間、原稿のフォルダに `.overleaf-compiler-serve.json`（ポート番号）を置く。
  `check` はそのポートの `/api/settle` に主文書の絶対パスを渡し、serve はそれが自分の開いている原稿のときだけ、
  **呼ばれた後に始まった周回（変更の確認）が終わるまで**待って組版の状態を返す（周回の途中で呼ばれると、その周回は
  直す前の更新時刻で判定しているかもしれないので、今の周回＋1周を待つ）。別の原稿を開いている・止まっている・
  印だけが残っている場合は断られるか繋がらないので、`check` が自分で組む。`build` と `clean` は同じ問い合わせで、
  serve が組んでいれば断る
- **`check` は TeX 以外で止まった理由も出す。** 文献処理や dvipdfmx で止まると `.log` にエラーが無いので、
  latexmk の出力から理由の行を拾う
- **`check` のはみ出しのファイル名は `.log` の括弧の入れ子から推定する。** TeX は Overfull に
  ファイル名を付けないため。段落が `\input` をまたぐ場合は、段落が終わったファイルの行になる
- **export は、latexmkrc が無い原稿に推定したエンジンの `latexmkrc` を最上位に足す。**
  Overleaf の既定は pdfLaTeX で、和文の原稿はそのままでは通らない。Overleaf が読むのは最上位の
  latexmkrc だけなので、主文書がサブフォルダにある場合は警告する
